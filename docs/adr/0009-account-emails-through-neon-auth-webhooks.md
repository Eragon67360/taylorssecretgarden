# Account emails are sent by the site, through Neon Auth's webhooks

Neon Auth sent the account emails (a code to confirm an address, a link to reset a password; #82, #118) itself, through our SMTP on production, in its own unbranded template, and its console has no template editor. Its documented way to change them ([Customize emails](https://neon.com/docs/auth/guides/customize-emails)) is a webhook: with the production branch subscribed to `send.otp` and `send.magic_link`, Neon Auth skips its email and calls `app/api/auth-email` with the code or link, and the site sends it in the journal's look through Resend's API (#167). This takes back part of [ADR-0004](0004-neon-auth-replaces-clerk.md)'s "account emails come from our own SMTP".

- **Neon Auth does not fall back on its own email.** `send.otp` and `send.magic_link` are blocking events: if no attempt succeeds (3 attempts, at once, within 15 seconds; a 5xx, 408, 429 or a timeout is tried again, any other 4xx is final), the Member's request fails with an error. So the route answers 2xx only once Resend took the email, 502 when Resend failed (Neon tries again; the event id is Resend's `Idempotency-Key`, so a retry never sends twice), 503 when `RESEND_API_KEY` or `NEON_AUTH_BASE_URL` is missing, and 422, final, for a signed payload it cannot read. A Resend failure, a missing `RESEND_API_KEY` and an unreadable payload alert the owner (`service/owner-alerts.ts`) with what kind of email and why, never who; a missing `NEON_AUTH_BASE_URL` is only logged, since no call can be verified without it. To go back to Neon Auth's own emails, disable the webhook in the Neon console.
- **Only Neon Auth gets through**: every call must carry Neon Auth's Ed25519 signature (a detached JWS over the timestamp and the raw body, the key from the branch's JWKS by its kid), with a timestamp within five minutes; anything else is 401 with no detail. The JWKS is cached in memory for 10 minutes and fetched again for an unknown kid at most every 30 seconds (`lib/auth/webhook-signature.ts`). Node's `crypto` verifies it: no JOSE library.
- **Outside `/api/auth`**: that path is the proxy to Neon Auth, guarded by BotID for the browser's requests; Neon Auth's server has no BotID token and its call must not be proxied anywhere.
- **Hand-written table HTML** (`lib/emails/`), not React Email or MJML: two emails in use, one layout, no dependency, and the output is plain strings the unit tests read. A plain-text version goes with every email. English only: the payload carries no locale.
- **The site now handles the address and the code or link** for the time it takes to send them, and Resend receives them from the site rather than from Neon Auth; the privacy policy says so. Nothing is stored or logged: the logs and alerts name the kind of email and Resend's error, never the address, name, code or link.
- **Production only**: webhooks are configured per Neon branch. Development branches keep Neon's shared sender; `RESEND_API_KEY` is set for Production only.
