# The app connects as a least-privilege role; Neon Auth's schema is closed to it but for one function

The deployed app connected to Postgres as `neondb_owner`, which, being a member of the `neon_auth` role, can read and change every Neon Auth table: emails, password hashes, sessions. A flaw anywhere in the app (an injection, a bug in a raw query) would have had all of that within reach. The owner agreed (2026-10-01, #83) to a role of its own for the running app.

- **`swiftter_app`** ([`db/roles/swiftter_app.sql`](../../db/roles/swiftter_app.sql)): `LOGIN` and nothing else (no `CREATEROLE`, `CREATEDB`, `BYPASSRLS`, no membership), `CONNECT`, `USAGE` on `public`, `SELECT, INSERT, UPDATE, DELETE` on its tables and default privileges for the tables later migrations create (they run as `neondb_owner`). No `TRUNCATE`, no DDL, no `neon_auth`, no `drizzle`. Created in SQL, not in the Neon console, whose roles are members of `neon_superuser`.
- **A script, not a migration**: roles and their passwords belong to each Neon branch, and a password must never be committed. The owner runs it once per long-lived branch (README, "Database roles"); branches made from production afterwards inherit the role.
- **Account deletion goes through `public.delete_auth_user(text)`** (migration 0005), the app's only way into `neon_auth`: `SECURITY DEFINER` (it runs with `neondb_owner`'s rights), a fixed `search_path`, `EXECUTE` revoked from `PUBLIC` and granted to `swiftter_app` only; it deletes at most one `neon_auth."user"` row by id (sessions, credentials, memberships and invitations follow, on delete cascade) and deletes nothing for an id that is not a UUID. ADR-0007's exception to ADR-0004 stays as narrow as it was; what changes is that it is now the only thing the app's role can do there. Someone holding the app's credentials could still delete an account whose id they know, but read none.
- **The owner keeps everything else**: migrations (Migrate production, CI), the backup, and the seed scripts (`scripts/seed.ts` and `scripts/unseed.ts` read and write `neon_auth` on development branches) connect as `neondb_owner`, through Neon's API or `.env.local`. Vercel's Production and Preview `DATABASE_URL` use the role; Development (`.env.local`) stays on the owner, since local work migrates and seeds.
- **Rollback**: point `DATABASE_URL` back at the owner and redeploy. `drizzle/down/0005_delete_auth_user.down.sql` is only for rolling the code back past 0005, and only once the app is on the owner again.

Proven on the `dev` branch before release (the role made with a throwaway password, dropped afterwards): the integration suite passes as `swiftter_app`, which is refused `neon_auth` and `drizzle` (permission denied) and deletes an account through the function.
